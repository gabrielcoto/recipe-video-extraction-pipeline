# План реальной проверки извлечения

Автоматические тесты (`make test`) подменяют внешние вызовы и проверяют поведение, контракт и границы, но не доказывают качество распознавания на настоящих видео. Этот документ — протокол недостающей проверки: реальные URL, реальные модели, три типа входа. Пункты соответствуют позициям 2 и 10 в [src/TODO.md](../src/TODO.md) и рубрике приёмки [evaluation.md](evaluation.md).

## Набор видео: три типа входа

Источники информации в видео — речь (STT) и надписи на экране (OCR). Набор приёмки покрывает все три сочетания:

| Тип | Речь | Надписи | Что проверяет |
| --- | --- | --- | --- |
| Только текст | нет (музыка или тишина) | да | OCR-путь; STT не должен выдумывать текст из музыки |
| Только аудио | да | нет | STT-путь; пустой OCR не должен ломать сборку рецепта |
| Сочетание | да | да | слияние двух источников в `fusion.py` без дублирования и противоречий |

Первое видео набора:

| Свойство | `tomatoChickpea.mp4` |
| --- | --- |
| Тип | только текст («no-talking» формат: рецепт в надписях, звук — музыка) |
| Длительность | 72 с (лимит 180 с — с запасом) |
| Формат | 720×1280 (вертикальное), H.264 + AAC, 18 МБ |
| Надписи | заголовок «Creamy chickpea skillet», подписи шагов («Spices + chickpeas») и ингредиентов |
| Ожидаемое поведение | расшифровка пустая или почти пустая (`vad_filter=True` отсекает музыку); рецепт собирается из OCR |

Осталось подобрать: видео «только аудио» (голос-за-кадром, надписей нет) и «сочетание» (голос + надписи) с разрешённым использованием. На каждом слоте — один формат метки в таблице выше.

## Подготовка набора

1. Положи MP4 в `data/input_videos/`, скопируй `manifest.example.json` в `manifest.json` и заполни источник, права, длительность и путь к разметке (правила — в [data/input_videos/README.md](../data/input_videos/README.md)).
2. Вручную выпиши эталоны в `data/expected_outputs/<имя>.json` по содержимому видео — только подтверждённые роликом сведения, неизвестное — `null`. Синтетические `pasta.json`, `omelette.json`, `salad.json` заменить или удалить из набора.
3. Проверь эталоны контрактом:

```bash
.venv/bin/python -m fropti_core_contracts data/expected_outputs/*.json
.venv/bin/python scripts/compare_gold.py --validate-only data/expected_outputs/*.json
```

4. Зафиксируй нормализацию **до** прогонов: регистр и пробелы, единицы, обработка неизвестных значений. Рекомендуемый пресет для `compare_gold.py`: `--exclude /source --absent-equals-null`; выбор запиши в `data/input_videos/provenance.md` вместе с автором видео, датой получения и автором разметки. После прогона нормализацию не менять.

## Протокол прогона (для каждого видео)

Для каждого видео выполнить оба способа ввода и сохранить артефакты:

```bash
# 1. CLI, локальный файл
.venv/bin/python -m src.main --file data/input_videos/tomatoChickpea.mp4 \
  > runs/tomatoChickpea.file.json

# 2. API, локальный файл
make run
curl -s -X POST http://localhost:8000/extract/upload \
  -F 'file=@data/input_videos/tomatoChickpea.mp4' \
  > runs/tomatoChickpea.upload.json

# 3. URL (если видео доступно на согласованной платформе)
curl -s -X POST http://localhost:8000/extract \
  -H 'Content-Type: application/json' \
  -d '{"url": "https://..."}' \
  > runs/tomatoChickpea.url.json

# 4. Сравнение с эталоном
.venv/bin/python scripts/compare_gold.py --exclude /source --absent-equals-null \
  data/expected_outputs/tomatoChickpea.json runs/tomatoChickpea.file.json
```

Для каждого прогона зафиксировать: дату, команду, снимок настроек (без `LLM_API_KEY`), версии моделей (fastest-whisper/пакетов — `pip freeze`), результат `compare_gold.py` (числитель, знаменатель, процент, список расхождений). Промежуточные артефакты — расшифровка речи и текст с экрана — приложить в обезличенном виде: по ним видно, из какого источника пришёл каждый факт рецепта. Куда складывать: папка `runs/` в корне (в репозиторий коммитить только обезличенные артефакты).

## Проверка URL отдельно

Для URL достаточно одной заранее согласованной платформы. Перед прогоном:

- в контейнере `node --version` должен показывать 22.x (`docker compose -f docker-compose.full.yml build api` после обновления образа);
- платформа должна входить в `ALLOWED_URL_HOSTS` (по умолчанию — домены YouTube);
- видео — в пределах 180 с и 100 МиБ (`MAX_DOWNLOAD_BYTES`).

Ответ «Sign in to confirm you're not a bot» — ограничение IP со стороны YouTube, а не дефект кода; повторить позже или с другого IP. Cookies и обход ограничений в проект не добавляются ([SECURITY.md](../SECURITY.md)). Неудачные попытки фиксировать с причиной — они входят в отчёт как ограничение платформы, а не как провал извлечения.

## Критерии готовности проверки

- [ ] Три видео покрывают все три типа входа; у каждого есть источник, права и ручной эталон.
- [ ] Каждый эталон проходит `fropti_core_contracts` и `compare_gold.py --validate-only`.
- [ ] Для каждого видео: `POST /extract/upload` и CLI вернули `200`/код `0` с валидным `Recipe`; для согласованной платформы — `POST /extract` по URL.
- [ ] 100% успешных ответов проходят общий `Recipe`; совпадение с эталоном ≥80% путей по метрике [evaluation.md](evaluation.md#как-считать-совпадение-полей) для каждого видео.
- [ ] Приложены: команды, обезличенные промежуточные артефакты, отчёты `compare_gold.py`, демонстрационный ролик до 4 минут по [PR-шаблону](../.github/pull_request_template.md).

Результат набора демонстрирует качество на этих трёх видео и не обобщается на все видео и платформы.
